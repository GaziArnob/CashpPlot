Security Self-Assessment Report

CashPilot: an AI financial assistant for small businesses · Oct 20, 2026 · @Arnob
Contents: (1) permission-tier implementation, (2) known-risk list, (3) verification evidence.
Scope and method. This is a self-assessment by the development team, based on reading the implementation, 264 automated tests, and a scripted sandbox run against the real API (see section 3). It is not an independent penetration test and makes no claim of certification. Items marked planned are not built.

1. Permission-tier implementation

Access is decided in five layers. A request must pass all of them; each layer is a separate piece of code, so one mistake does not open everything.

#LayerImplementationWhere
1AuthenticationBearer JWT (15-minute lifetime) checked on every protected route; refresh token rotates and can be revokeddeps.get_current_user
2RoleThe user's role (owner, staff) is checked; owner-only routes return HTTP 403 for staffdeps.require_owner
3PlanPremium features (11 of them, such as the Cash Advisor, credit score and AI agent) are checked against the business's plan; otherwise HTTP 402 with an "Upgrade to Pro" messagedeps.needs, plans.py
4Business scoping and object ownershipEvery query filters by the business of the signed-in user, never by an id from the request; any id in a URL is verified to belong to that business before it is read or changeddeps.get_business, deps.owned
5Database row-level securityPostgreSQL policies on every table with a business_id: a request only sees rows of its own business even if a query forgets the filter. Forced on the table owner too. A start-up warning fires if the database role would skip RLSmigration 0005, db.py

1.3 Authentication details

  • Passwords: bcrypt, cost 12. The account locks for 15 minutes after 5 failed sign-ins. Rate limits on auth requests (10 per minute).
  • Tokens: access JWT 15 minutes; refresh token 7 days, rotating, in an httpOnly, secure, SameSite=Strict cookie, and the refresh route also requires a custom header against CSRF.
  • Optional second factor: authenticator-app code (TOTP). SMS codes are not used.

2. Known-risk list

Severity is the team's own judgement of the impact for a financial product if the risk is exploited: High, Medium, Low.

IDRiskSeverityWhat is in place nowStatus / next step
R1No independent penetration test or auditMediumSelf-review, 264 automated tests, sandbox run with isolation checksPlanned: external review before real customer money or data
R2Rate limiter is in memory: it is per server process and resets on restartMediumLimits per client address and signed-in user; account lockout is stored in the database and is not affectedPlanned: Redis-backed limiter for several workers
R3The access token is kept in the browser's sessionStorage, so a cross-site scripting bug could read itMediumShort 15-minute lifetime; React escapes output; the API sends a strict content-security-policy; the long-lived refresh token is httpOnly and not readable by scriptsPlanned: a content-security-policy on the web client, and keeping the access token in memory only
R4JWTs are signed with one shared secret (HS256); if it leaked, tokens could be forgedMediumSecret only in server environment variables, never in git or the client; refresh tokens are also checked against a stored id and can be revokedPlanned: secret rotation procedure; asymmetric signing

R10Row-level security only works if the database role is not a superuserMediumApplication-level business scoping still applies on every query; the API logs a warning at start-up if the role would skip RLS; tested on PostgreSQLMitigated by the start-up check; deployment guide tells how to create a plain role
